# Hatchet execution engine

Factory uses Hatchet's Go SDK for durable execution. One Factory execution is one Hatchet durable task. It follows the pinned workflow's routes, starts each run step as a child task, waits for scoped decision events, and waits for an explicit retry event when a package exhausts its automatic tries. A route back to an earlier step creates a new visit.

Factory defaults to Hatchet's open-source embedded engine. It starts inside the local Factory service with bundled Postgres and no client token or separate server. The daemon uses the Factory runtime directory as its working directory, so the embedded engine's default per-directory data location is stable across CLI calls. The embedded engine stops with the Factory service. The first explicit `factory start` downloads and initializes PostgreSQL and applies database migrations; subsequent starts reuse persisted data. Operational commands never start the service. `factory stop` requests shutdown and waits for service cleanup, including database shutdown. Clients share one service per user, with startup serialized across terminals to prevent competing database owners.

Factory's schema is separate from Hatchet's. Versioned SQL migrations live in [`internal/state/migrations/`](../internal/state/migrations/) and are applied with go-migrate before the Factory service accepts work. Add the next numbered `.up.sql` and `.down.sql` pair for schema changes; do not edit an applied migration. Migration history is stored in `public.factory_schema_migrations`. A failed or dirty migration prevents startup; Factory does not silently reset the version. The first migration also recognizes tables created by the earlier startup DDL without deleting their records.

The durable execution has an explicit one-year timeout because it can wait for human decisions or retries. Each agent package invocation has a separate two-hour timeout. These replace the engine's five-minute default. A failed execution records its reason and stops any still-running local agent sessions. Restart the Factory service after changing task registration options so its worker registers the new limits.

For a separate **self-hosted** Hatchet server, the service operator explicitly sets `FACTORY_HATCHET_MODE=self-hosted`, the `HATCHET_CLIENT_*` values supplied by that server, and `FACTORY_DATABASE_URL` for Factory's own PostgreSQL schema. The client token and database URL are internal service credentials. Workflow users do not supply them to `factory` or put them in `factory.yaml`. Hatchet Cloud is out of scope. The pinned SDK currently requires Go 1.26.10; the Go tool may download that toolchain automatically.

`hatchetengine.New` takes a Hatchet client, an `execution.Runner`, and an optional `execution.Observer`. The adapter implements the control plane's `execution.Engine` interface. `Start` submits an immutable configuration and returns a Factory execution ID and an opaque workflow run ID. The public CLI uses the controller's operations; it does not push Hatchet events directly. A package must return a structured `StepResult`; the engine validates its route and required artifacts before accepting it. The controller and package runner do not import Hatchet; only this adapter and the application wiring know it is the current scheduler.

Stage policy is pinned with the workflow. The durable engine counts completed rounds when a step routes back to a stage's first run step. It routes a limit-exhausted stage to its configured human decision, if required, and records `stage_limit_reached`; otherwise it fails the execution. This logic lives in the scheduler-neutral `execution.StageRouter` so replay and a future engine use the same policy.

Current limits: the controller is for a trusted local user and does not authenticate decision authority; request IDs and version checks are not yet enforced; configuration continuation and result supersession are not implemented. Factory record updates are transactional, but a Factory transition and its Hatchet event are not one transaction. Reconciliation after a crash needs more work. Input snapshots and agent result artifacts remain local working files, so deployment across hosts requires shared artifact storage or worker-side materialization. The host command runner is not isolated and rejects access profiles it cannot enforce. Package digest checks prevent silent changes to agent bundles, but the bytes are not yet stored in a package registry.

Concurrent loops use `RunMany` to allocate all child invocations before awaiting results. Result waits can run together without allocating replay-sensitive actions in completion order. Routing and retry waits use configuration order. Each accepted member result comes from the shared communication service; the runner recovers it on replay instead of relaunching the process. A failed member interrupts peers through the observer and pauses the whole round for an explicit retry. The service reserves group capacity against the worker's package-slot count before process startup.

Migrations `000003_comms` and `000004_publications` add conversations, participants, per-recipient cursors, idempotency receipts, requests, and exact publication bytes. Runtime MCP credentials do not expose internal engine credentials. The service API version detects old running binaries after this contract change.

## Hook scheduling boundary

The worker registers a separate utility task alongside execution and package tasks. The host exposes `execution.HookRunner`; `internal/hooks` implements it through supervised processes and persistent control-plane records without importing Hatchet. Hook JSON context and identity are scheduler-neutral. The durable graph places each hook at its execution/stage/step boundary, reuses successful task results on replay, and waits for the existing scoped retry event when a hook blocks. There is no Git code in the scheduler. See [lifecycle hooks](hooks.md).
